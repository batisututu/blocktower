- 실행일: 2026-09-20
- 판정: **조각 공급 예제·배치/종료 판정·RNG 복원 검사는 통과했다. 실험용 프로토타입의 기반으로 사용할 수 있다.**
- 대상: [조각 공급 v0.1](Blocktower_Piece_Supply_Spec.md)의 자체 작성 GDScript. 실제 게임·저장 시스템·모바일 화면은 아직 대상이 아니다.
- 엔진: `4.7.2.stable.official.ed1daf0bf`, GUT: `v9.7.1` / `aeb5d4f3f7f0a6c9b5e178876d6c99b791fda605`

## 2. 검증 방법과 증거

공식 [Godot 4.7.2 배포 페이지](https://godotengine.org/download/archive/4.7.2-stable/)에서 Windows 배포본을 확인하고 별도 임시 경로에 준비했다. 다운로드한 ZIP의 SHA-256을 GitHub 공식 릴리스 자산 digest와 대조했다. 기존 PATH의 Godot 4.6.1이나 export templates를 교체하지 않았다.

- Godot ZIP SHA-256: `731980f9608d61333e5baf54a2ef17210acc7a538446c0cb9969f002aca1e953`
- GUT은 [고정 릴리스](https://github.com/bitwes/Gut/releases/tag/v9.7.1)의 커밋으로 가져와 임시 프로젝트에만 배치했다.
- Python의 집합 포함 관계로 독립적인 배치 정답을 계산하고 실제 GDScript 출력과 대조했다. 도형 정의는 동일 데이터를 공유하되 판정 알고리즘은 분리했다.
- 빈 보드·고밀도·체커보드·단일 완성 행/열·교차 줄, 잘못된 보드 크기/값, 빈 큐·알 수 없는 ID·4개 큐 등을 포함했다.
- 두 번째 Godot 프로세스가 JSON에 저장된 seed/state에서 다음 10묶음을 생성하고 첫 프로세스의 실제 ID/최종 state와 비교했다. 모든 문자열을 일반 파일에 남겼으며 프로세스 메모리를 공유하지 않았다.

## 3. 분포와 중복: 확인된 차이

각 정책에서 20개 고정 시드로 50,000묶음을 추첨했다. 전체 ID 19개와 각 슬롯의 ID 19개, 총 76개 구간을 확인했다. 각 구간의 관측값과 기대값 차이를 이항 표준편차로 나눈 절댓값이 6 이하인지 검사했다. 중복 묶음 비율도 별도 검사했다. 이는 큰 편향을 찾기 위한 통계 점검이며 무작위성이나 재미의 증명이 아니다.

| 항목 | 계열 가중 v0.1 | ID 균등 v0.1 |
|---|---:|---:|
| 추첨 조각 수 | 150,000 | 150,000 |
| 가장 큰 표준화 편차 | 2.488 | 2.695 |
| 동일 ID가 2개 이상인 묶음, 이론값 | 19.984% | 15.235% |
| 동일 ID가 2개 이상인 묶음, 관측값 | 19.590% | 15.422% |

중복 이론값은 개별 ID 확률을 p라고 할 때 `3 × Σp² − 2 × Σp³`로 계산했다. 방향이 다른 같은 계열을 중복으로 센 값은 아니다.

**가중 정책은 약 다섯 묶음 중 하나에 같은 ID가 반복될 수 있다.** 이는 현재 '복원 추첨·중복 허용' 명세의 결과다. 이용자가 반복을 불쾌하게 느끼는지는 첫 플레이 관찰에서 확인해야 한다. 이번 결과만으로 중복 제한이나 쉬운 조각 보정을 자동 채택하지 않는다.

## 4. 무엇을 통과했고, 무엇이 남았는가

확인한 범위에서는 코드 수정이 필요한 불일치를 발견하지 못했다. 기본 추첨·좌표·현재 배치 가능 여부·수동 대기 줄 우선 처리·저장된 RNG 복원과 GUT 기본 실행을 구현 시작의 근거로 사용할 수 있다.

| 남은 항목 | 이번 검사로 판단할 수 없는 이유 | 다음 검증 |
|---|---|---|
| 실제 퍼즐 난이도·자동/수동 밸런스 | 사람/봇의 전체 플레이를 수행하지 않음 | 동일 정책·시드에서 첫 10/30층과 게임오버 관찰 |
| 점수·성장·묶음 스트릭 | 공급 예제에는 전체 게임 상태 전이가 없음 | GameSession 구현과 통합 사례 |
| 원자적 저장·강제 종료·중복 보상 | 이번 복원은 RNG JSON을 다시 읽는 검사이며 파일 커밋 구현이 아님 | 쓰기/교체 전후 장애 주입 |
| 터치·프리뷰·모션 감소·음향 | 헤드리스 검사에는 실제 HUD가 없음 | 최소 플레이 화면과 기기 확인 |
| Android/iOS 빌드·메모리·프레임 | 에디터의 데이터 검사만 실행 | 플랫폼 템플릿·SDK·기기 검사 |
| GUT의 모든 기능 | 기본 테스트/CLI만 확인 | mock/double 등 실제 도입 기능에 맞춰 추가 |
| 데이터 변경 후 저장 호환 | 이번에는 카탈로그와 정책이 고정 | 버전 변경·구버전 저장 fixture 검증 |

보드 적합 후보 강제 공급, 3조각 해 존재 보장, 중복 제한은 여전히 미채택이다. 수동 모드의 '대기 줄이 있으면 종료하지 않는다'를 지키는 판정과 '항상 풀 수 있게 공급한다'를 혼동하지 않는다.

## 5. 다시 실행하기

프로젝트 루트에서 PowerShell로 실행한다. 실행 도구는 표준 Python 라이브러리만 사용하고, 정확한 Godot 버전이 아니면 중단한다.

```powershell
python -X utf8 docs/pretests/run_preflight.py --godot "C:/Users/batis/AppData/Local/Temp/blocktower-preflight-20260920/engine/Godot_v4.7.2-stable_win64_console.exe"
```

임시 엔진 경로가 정리되면 별도로 준비한 4.7.2 실행 파일의 경로를 넘긴다. 엔진을 자동 다운로드하거나 PATH를 바꾸는 스크립트는 아니다. 결과 JSON은 같은 경로에 갱신되므로 비교가 필요하면 이전 결과를 보존한다.

GUT 검사는 4.7.2 검사 프로젝트 안에 `examples/piece_supply_v0_1.gd`, `tests/test_supply_gut.gd`, 해당 커밋의 `addons/gut`를 배치한 뒤 import와 테스트를 순서대로 실행한다. 실제 명령과 로그는 위 GUT 기록에 있다.

`pretests/results/play_data.json`은 목표 엔진에서 생성한 카탈로그와 고정 시드별 공급열이다. 후속 플레이 화면에서 동일 공급을 사용하는 데 쓸 수 있는 데이터이며, 플레이 화면 자체나 사용자 테스트 완료를 뜻하지 않는다.
