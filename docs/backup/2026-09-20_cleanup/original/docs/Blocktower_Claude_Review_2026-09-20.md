## 1. 게임오버 정의 — 채택

### 1.1 문제 재확인

상위기획 §6의 세 번째 조건 "대기 줄 제거 후에도 **남은 블록을 모두** 배치할 수 없음"은 두 가지로 읽힌다.

- (a) 남은 블록 중 하나도 놓을 수 없음 → 올바른 게임오버
- (b) 남은 블록을 전부 순서대로 놓을 수 없음 → 오판. 하나를 놓으면 줄이 완성되어 공간이 생길 수 있으므로 미래를 알 수 없고, 조기 종료가 된다.

Codex의 "하나도 배치 불가 AND 대기 줄 없음" 정의가 맞다. 아래처럼 판정기 형태로 문서화하기를 권한다.

### 1.2 제안: 3상태 판정기

```
enum TurnState { CONTINUE, MUST_CLEAR, GAME_OVER }

func evaluate(board, queue) -> TurnState:
    # queue: 아직 배치하지 않은 블록 1~3개
    # pending_lines: 현재 보드에서 완성된 가로/세로 줄 (보드에서 파생, §10-F 참조)
    if queue.any(block => board.has_any_valid_position(block)):
        return CONTINUE
    if board.pending_lines().size() > 0:
        return MUST_CLEAR      # 수동 모드에서만 도달 가능
    return GAME_OVER
```

- 판정 시점: 배치 직후, 클리어 직후(버튼·자동·전환 확인창 모두), 모드 전환 직후, 묶음 갱신 직후, 세이브 복귀 직후.
- MUST_CLEAR 상태: 블록 드래그는 허용하되 어디에도 놓이지 않으므로 클리어 버튼을 강조(펄스)하고 안내 문구를 띄운다. 자동 강제 클리어는 하지 않는다(이용자 결정권 유지).
- 자동 모드는 대기 줄이 존재할 수 없으므로 판정이 CONTINUE / GAME_OVER 둘로 축소된다. 별도 규칙이 아니라 같은 판정기의 특수 경우다.
- 묶음 경계: 3개 중 2개를 썼고 마지막 1개가 어디에도 안 들어가면 게임오버다. "다 쓰기 전에는 새 묶음이 오지 않는다"는 §3.1 규칙을 이 절에 교차 참조하면 오해가 줄어든다.

### 1.3 검증 기준

| ID | 상태 | 기대 |
|---|---|---|
| GO-1 | 빈칸 없음, 대기 1줄, 블록 3개 남음 | MUST_CLEAR (게임오버 아님) |
| GO-2 | GO-1에서 클리어 후에도 어떤 블록도 못 놓음 | GAME_OVER |
| GO-3 | 블록 2개 남음, 그중 1개만 놓을 수 있음 | CONTINUE ("모두" 오독 방지 케이스) |
| GO-4 | 블록 1개 남음, 못 놓음, 대기 줄 없음 | GAME_OVER (묶음 갱신 없음) |

## 2. 교차 줄·셀 합집합·16줄 경계·원자 저장 — 채택 + 보완

### 2.1 정의 명문화 (상위기획 §4.2, §5.2, §8에 삽입 권고)

- **클리어 이벤트**: 한 번의 클리어 행위. 자동 모드는 배치 1회로 유발된 제거, 수동 모드는 버튼 1회 또는 전환 확인창 확정 1회.
- **줄 수 L** = 완성 가로줄 수 R + 완성 세로줄 수 C.
- **제거 셀** = 해당 줄들의 셀 **합집합**. 셀 수 = 8R + 8C − R·C.
- 점수 = L × 100 × 배율(L). 층 = L. 재질 진행 = 조건 충족 시 L. 세 값 모두 **셀 수가 아니라 줄 수** 기준임을 명시.
- 확인창(§4.4)의 "이번 클리어: +XXX점"은 버튼과 동일 함수로 계산.

예시(문서 표에 추가 권고):

| R | C | L | 제거 셀 | 점수 | 층 |
|---:|---:|---:|---:|---:|---:|
| 1 | 1 | 2 | 15 | 240 | +2 |
| 2 | 2 | 4 | 28 | 640 | +4 |
| 3 | 3 | 6 | 39 | 960 | +6 |
| 8 | 8 | 16 | 64 | 2,560 | +16 |

### 2.2 16줄 경계

- 수동 모드 최대 L = 16 (보드 64칸 만실). 자동 모드 최대 L은 블록 형상에 종속되며 3×3 또는 I-5 기준 6.
- 층·진행도에 별도 상한을 두지 않아도 된다. 16이 자연 상한이며 배율은 ×1.6에서 이미 멈춘다.
- 다만 만실 클리어는 수동 모드 전용 성과라는 점을 §5.2 근처에 명시해 두면 §10-D(수동 점수 우위)와 함께 읽힌다.

### 2.3 원자 저장의 근거를 익스플로잇으로 서술

Codex의 "보상 원자 저장" 자체는 맞지만, 문서에는 **왜** 필요한지가 있어야 구현 담당이 타협하지 않는다. 구체적 시나리오 두 개를 넣기를 권한다.

1. 클리어 버튼 → 성장(층·진행도) 저장 → 보드 저장 전에 앱 강제 종료 → 복귀하면 대기 줄이 그대로 남아 있음 → 다시 클리어 → **층수·진행도 2배** (복제 익스플로잇).
2. 반대 순서면 → 보드는 지워졌는데 층수는 안 올라감 → **성과 손실** (VOC 최악 케이스).

### 2.4 저장 메커니즘 제안 (상위기획 §29 보강)

1. 클리어 처리는 순수 함수 `(state) → (new_state, clear_event)` 로 작성.
2. `new_state` 전체(보드·큐·점수·성장·주간·시퀀스)를 **단일 파일**로 직렬화.
3. 임시 파일에 기록 → close → rename으로 교체. Godot 4에서는 `FileAccess` 기록 후 `DirAccess.rename_absolute()`. 동일 파일시스템 내 rename은 원자적이다.
4. 파일 내부에 `schema_version`, `clear_event_seq`(단조 증가), `checksum` 포함.
5. 직전 파일을 `.bak`로 보존. 로드 실패(체크섬 불일치·잘림) 시 `.bak` 복구.
6. 저장 시점: 모든 배치·클리어·전환·묶음 갱신 **직후** + `NOTIFICATION_APPLICATION_PAUSED`. 상태가 작으므로(64셀 + 블록 3 + 정수 수십 개) 매 행동 저장이 가능하다. "백그라운드 전환 시 저장"만으로는 Android 프로세스 킬을 못 막는다.

### 2.5 검증 기준

| ID | 시나리오 | 기대 |
|---|---|---|
| SV-1 | 배치 직후 프로세스 강제 종료 → 복귀 | 보드·큐·점수 일치 |
| SV-2 | 수동 클리어 직후 강제 종료 → 복귀 | `clear_event_seq` 1 증가, 층수 1회만 반영, 대기 줄 없음 |

## 3. 파츠의 동시클리어 강제 — 채택 (수정)

### 3.1 문제 재확인

성장기획 §8의 파츠 해금은 "벽돌 진행도 10/30/60/100"이고, 진행도는 §6에서 "2줄 이상 동시 클리어에서 제거한 줄 수"로 정의된다. 즉 재질 **기본 해금**만 누적 대체 경로가 있고, 파츠는 전부 동시 클리어 전용이다. 성장기획 §17 "특정 외형 때문에 수동 모드 강제"를 피한다는 원칙과 정면 충돌한다. 특히 크리스털 파츠(4줄 이상)는 자동 모드에서 사실상 도달 불가다.

Codex 지적은 옳다.

### 3.2 반론: 전부 이중 경로로 만들면 "빠른 경로 = 도전 목표"가 사라진다

상위기획 §10 "숙련 이용자는 도전으로 더 빠르게 해금 가능"과 성장기획 §18 검증 3 "빠른 해금은 도전 목표로 느끼고"를 살리려면 동시 클리어 전용 보상이 **조금은** 남아야 한다. 제안:

- **규칙**: 모든 파츠는 `(재질 진행도 ≥ X) OR (누적 제거 줄 ≥ Y)` 로 해금.
- **예외**: 재질당 최대 1개 **프레스티지 파츠**(예: 랜드마크형 외벽, 판타지 랜드마크)만 진행도 전용. 조건: 해당 파츠가 없어도 구간이 "완성"으로 보여야 한다(실루엣 필수 요소 금지).
- **Y 산정**: 시뮬레이션에서 자동 모드의 "조건 충족 줄 비율 p"를 구해 `Y ≈ X / p`. p 미측정 시 가안 벽돌 0.4, 금속·유리 0.15, 크리스털 0.05. 이 가안은 검증 전까지 문서에 "가정"으로 표기.

대안 B(참고): 진행도 정의 자체를 `누적 L × 배율(L)` 하나로 바꾸면 트랙이 하나로 줄고 큰 클리어가 여전히 유리하다. 다만 "크리스털 = 4줄의 성취"라는 재질별 정체성이 사라지므로 A안 튜닝이 실패했을 때의 대안으로만 둔다.

### 3.3 검증 기준

- 자동 모드만 사용하는 시뮬레이션 이용자가 벽돌·금속·크리스털의 비프레스티지 파츠 전부를 누적 ≤ 1,000줄 안에 해금 가능한지(수치는 §9 시뮬레이션 결과로 확정).
- 프레스티지 파츠를 뺀 구간 외형이 완성으로 보이는지 목업으로 확인.
- 성장기획 §22-2 시뮬레이션 항목에 "파츠 포함"을 명시.

## 4. 연속 성과 중복 집계 방지 — 채택 + 보완

### 4.1 문제 재확인

상위기획 §13은 "새로운 줄"이라고만 쓰고 정의하지 않았다. 수동 모드에서 묶음 N에 완성한 줄 A는 묶음 N+1에도 완성 상태로 남아 있으므로, 상태 기준으로 세면 중복 집계된다. Codex 지적이 맞다.

### 4.2 제안: 전이 이벤트 기준

```
# 묶음 시작
batch_success = false

# 매 배치 직후
newly_completed = complete_lines(after) − complete_lines(before)
# before = 이 배치 직전 보드. 이미 대기 중인 줄은 before에 포함되어 있어 제외됨
if newly_completed.size() > 0:
    batch_success = true

# 묶음 종료 (3개 모두 배치)
streak = batch_success ? streak + 1 : 0
best_streak = max(best_streak, streak)
```

- 클리어(버튼·자동·확인창)는 전이를 만들지 않으므로 스트릭에 영향 없음.
- 스트릭은 판 시작 시 0. `best_streak`만 영구 저장(상위기획 §29와 일치).
- 게임오버로 묶음이 미완이면 증가 없이 종료.
- 자동 모드는 배치 직후 즉시 제거되지만 전이는 이미 기록되므로 동일 규칙으로 동작한다. 모드별 분기 불필요.
- 중간 저장 시 `batch_success`와 `streak`은 저장 대상(묶음 중간 복귀 대비).

### 4.3 검증 기준

| ID | 시나리오 | 기대 |
|---|---|---|
| ST-1 | 묶음 N에서 줄 A 완성(대기), 묶음 N+1에서 새 전이 없음 | N+1은 실패, 스트릭 0 |
| ST-2 | 묶음 N에서 A 완성·클리어, 묶음 N+1에서 같은 위치 재완성 | N+1 성공 (새 전이) |
| ST-3 | 배치 1회로 3줄 동시 전이 | 성공 1회 (줄 수 무관) |
| ST-4 | 자동/수동에서 같은 배치 순서 | 스트릭 결과 동일 |
| ST-5 | 묶음 중간 저장·복귀 후 완성 | 복귀 전 `batch_success` 반영 |

## 5. 오프라인 성장 vs 주간 랭킹 — 채택 (수정)

### 5.1 동의하는 부분

- 오프라인 우선(상위기획 §3.1)이면 층수는 클라이언트가 결정한다. 이 값을 그대로 쓰는 글로벌 랭킹은 세이브 편집만으로 무력화된다.
- 주차 경계도 기기 시각을 믿을 수 없다.
- 따라서 랭킹 신뢰 설계는 Phase 4로 미루는 데 동의한다.

### 5.2 반론: 데이터 계약은 미룰 수 없다

랭킹을 나중에 검증하려면 게임이 **재생 가능**해야 하고, 이것은 Phase 1 규칙 엔진 설계에서 결정된다. 나중에 붙일 수 없다. 아래 셋은 P0으로 상위기획 §29에 넣기를 권한다.

1. 블록 생성 RNG는 시드 기반. `rng_seed`, `batch_index`를 게임 상태에 저장.
2. 행동 로그: `(batch_index, slot, x, y)` 배치 기록, `CLEAR`, `TOGGLE` 이벤트. 판 종료 시 로그 + 최종 상태 요약을 저장.
3. 규칙 엔진은 순수 함수로 작성해 로그 재생으로 동일 점수·층수를 재현(결정론).

이 셋은 랭킹과 무관하게 **회귀 테스트 하네스**로 즉시 가치가 있다. 버그 리포트 = 로그 파일 하나가 된다.

### 5.3 주차 경계 제안

- 주차는 **서버 수신 시각** 기준(UTC 또는 KST 중 하나로 고정). 오프라인 획득분은 동기화된 시점의 주차에 귀속. 단순하고 설명 가능하며 기기 시각을 신뢰하지 않는다.
- 신뢰 단계: 친구 랭킹(검증 없음, 저위험) → 글로벌(서버 재생 검증 필수). 문서에 "글로벌 주간 랭킹은 서버 재생 검증 없이 출시하지 않는다"는 원칙 한 줄을 권한다.

### 5.4 검증 기준

- 임의의 판 로그를 규칙 엔진에 재생했을 때 점수·층수·클리어 이벤트 시퀀스가 100% 일치(자동 테스트).
- 같은 시드·같은 행동 로그를 두 기기에서 재생해 동일 결과.

## 6. 프리렌더 조합 폭증·지붕 충돌·부분구간 — 채택 + 대폭 보완

### 6.1 조합 폭증 수치화

상위기획 §16 편집 슬롯은 외벽·창문·난간·테라스·패턴·조명·상단 마감 7개다. 10층 구간을 **통짜 이미지**로 렌더하면 조합 수는 슬롯 옵션의 **곱**이다. 재질 4 × 창 3 × 난간 2 × 테라스 2 × 패턴 3 × 조명 2 × 상단 3 = 864장. 1인 개발 불가.

### 6.2 제안: 층 타일 + 레이어 합성

- **직교(orthographic) 고정 카메라**로 렌더. 상위기획 §20은 "고정 각도"만 말하는데, 원근 카메라면 높은 구간이 작아져 타일링이 깨진다. 직교 + 고정 각도(예: 고도 30°, 방위 45°)를 명시해야 한다.
- **층당 픽셀 상수** 정의(예: 기준 해상도에서 1층 = 24px). 모든 모듈이 이 격자에 맞아야 이어 붙일 수 있다.
- 구간 = `base(1) + floor × n + cap(1)`. `floor`는 1층 높이 모듈(외벽 + 창)이고 10번 타일링. 슬롯별 레이어(난간·테라스·조명·패턴)는 같은 카메라로 따로 렌더한 투명 PNG를 Godot에서 `Sprite2D` 스택으로 합성.
- 자산 수는 곱이 아니라 **합**이 된다. 재질 4 × (floor 1 + 창 3 + 난간 2 + 테라스 2 + 패턴 3 + 조명 2 + cap 3) ≈ 64장. Phase 3 MVP는 재질당 floor 1 + base 1 + cap 1 = 12장 + 비계 2장 + 정상 마감 4장 ≈ **18장**이면 된다.
- 레이어 간 그림자(테라스가 외벽에 드리우는 그림자)는 사라진다. 스타일라이즈드 룩으로 수용하거나 외벽에 범용 AO를 굽는다. 이건 Visual Bible 결정 사항으로 넘긴다.

### 6.3 지붕 중간층 충돌 → 슬롯 분리

구간마다 첨탑을 얹으면 다음 구간이 그 위에 올라갈 때 관통한다. 데이터 모델을 바꿔야 한다.

- **구간 슬롯 `cornice`(경계 마감)**: 코니스·띠·평평한 난간. 위에 무엇이 와도 안전.
- **탑 슬롯 `tower_cap`(정상 마감)**: 첨탑·안테나·스카이라인. 탑 전체에 하나. 새 구간이 시작되면 자동으로 위로 이동.
- 상위기획 §16 "상단 마감"과 §12의 "클래식 상단 장식 / 스카이라인형 상단 / 첨탑"을 두 슬롯으로 재분류.
- 미정: 대표 구간 출품 뷰(구간 단독 표시)에서 정상 마감을 보여줄지. 권고는 "평평한 코니스로 통일, 출품용 마감은 후순위."

### 6.4 부분 구간 표시 → 비계

23층 탑은 구간 3이 3/10이다. 통짜 렌더를 자르면 잘린 단면이 보인다. 제안:

- 진행 중 구간은 `scaffold_floor × n + scaffold_cap`(공사 중 비계·크레인)으로 표시. 자산 2장.
- 구간 완성 시 비계 → 완성 외형으로 전환. 이것이 곧 상위기획 §15의 "완성 전/후 비교"가 되어 별도 연출 자산이 필요 없다.
- 완성 직후 기본 외형 = 직전 구간 스타일 상속(또는 이용자가 지정한 기본 스타일). 편집을 강요하지 않으면서 탑이 누더기처럼 보이지 않는다.

### 6.5 전체 탑 뷰 LOD

3,000층 = 300구간. 화면 높이 2,400px에 맞추면 구간당 8px다. 스프라이트가 의미 없다.

- 줌 3단계: **구간 뷰**(풀 스프라이트) / **근접 전체 뷰**(≤ 10구간 풀 스프라이트 + 스크롤) / **원경 전체 뷰**(구간을 재질 색 띠로 그린 1px-per-floor 스트립 텍스처 + 안개).
- 상위기획 §17·§24 "안개/원근감"은 원경 전체 뷰의 기능 요구로 재기술.

### 6.6 검증 기준

- 재질 1종으로 floor 타일 10개 + base + cap을 이어 붙였을 때 이음새가 1px 이내(직교 카메라·픽셀 상수 검증).
- 구간 3개 + 비계 구간 1개 + tower_cap을 합성한 목업 1장.
- 300구간 원경 뷰가 중저사양 기기에서 60fps(스트립 텍스처 방식 확인).

## 7. 비교이미지 문제 — 채택 (수정)

### 7.1 확인된 사실

- **캡션 겹침 확인.** B 패널의 "Blocktower의 기본 아이덴티티"와 C 패널의 "층판/레이어 표현 강화"가 각 보드의 **8행째 블록**(y ≈ 730px / 1000px) 위에 겹쳐 있다. 보드 영역이 8행 높이보다 짧게 잡힌 레이아웃 오류다.
- **C 밴드 오인 가능성 동의.** C 블록은 각각 2~3개의 밝은 수평선을 갖는데, 한 행에 C 블록이 나란히 놓이면 수평선이 행 전체를 가로지르는 **연속 띠**가 된다. 이 게임의 핵심 상태 신호인 "완성 줄 대기"를 많은 게임이 수평 하이라이트 띠로 표현하므로 충돌한다.
- 이미지에는 **대기 줄 상태가 아예 없다.** 수동 클리어가 이 게임의 차별점인데, 그 상태의 시각 표현이 스킨 "확정" 근거에 빠져 있다.

### 7.2 수정 의견: 색각 검증의 초점

블록 색은 이 장르에서 게임플레이 정보가 아니다(어떤 색이든 칸을 채우면 줄이 된다). 따라서 6색 팔레트의 적록 문제는 우선순위가 낮다. 색각 검증은 다음 **상태 신호**에 집중해야 한다.

- 배치 프리뷰 유효/무효 (관행적으로 초록/빨강 → 색 외 채널 필요)
- 완성 줄 대기 하이라이트
- 클리어 버튼 활성/강조 상태
- MUST_CLEAR 안내

### 7.3 다음 목업 요구사항

- 실척 모바일 전체 화면 1080×2400(9:20), 안전 영역 포함.
- 요소: HUD(점수·최고점·자동 토글), 8×8 보드, `[N줄 클리어]` 버튼, 블록 큐 3개, 탑 성장 표시(`+3층`, `다음 구간까지 2층`).
- **최악 케이스 장면**: C 스킨에서 가로 2줄 + 세로 2줄이 교차 대기 중이고 프리뷰 고스트가 떠 있는 상태. 이 장면에서 대기 줄이 밴드와 구분되면 통과.
- B·C 동일 장면 나란히 + 색각 시뮬레이션(적록·청황) 3종.
- 클리어 버튼은 엄지 도달 범위 안에 있으면서 드롭 존과 인접하지 않을 것(블록을 놓다가 클리어를 눌러 되돌릴 수 없는 사고 방지). 배치는 미정 항목.

### 7.4 문서 상태 조정 권고

스킨결정 상태 "확정"은 실척 검증 전이라 이르다. **"형태 방향 확정 / 실척 가독성 검증 대기"**로 낮추고, 통과 조건을 §7.3으로 명시하기를 권한다.

## 8. C 유료 스킨 동등성·구매 복원 — 채택 + 보완

### 8.1 동등 규칙 명문화 (스킨결정 §4 보강)

"공통 유지 요소"에 다음을 추가해야 한다.

- 게임오버·MUST_CLEAR 안내 표시 지연 동일.

### 8.2 보완: 상태 신호는 스킨 범위에서 제외

스킨결정 §2 "C 스킨 포함 범위"에 **배치 Preview 스타일**과 **완성 줄 Highlight**가 들어 있다. 이 둘은 §7.2의 상태 신호 그 자체다. 제안:

### 8.3 구매 복원·오프라인 권한

상용 단계로 미루는 데 동의한다. 단, 두 가지는 지금 적어 두어야 한다.

- 세이브 스키마에 버전과 마이그레이션 규칙이 있어야 나중에 `skin_entitlements`를 무리 없이 추가한다(§10-E).

### 8.4 문서 간 불일치

상위기획 §32는 "수익모델" 미정인데 스킨결정은 "C 유료 코스메틱 확정"이다. 상위기획 §31 확정 사항에 "코스메틱 스킨 판매(C)"를 넣고, §32는 "광고·구독 등 기타 수익모델 미정"으로 좁히기를 권한다.

## 9. 첫 30층·블록 생성·MVP 종료기준 — 채택 + 보완

### 9.1 블록 생성 규칙은 P0이다

상위기획 §33에 "다음 과제 3순위"로 되어 있으나, 재질 누적 해금 30/100/250줄과 파츠 진행도 10/30/60/100은 **판당 줄 수**를 모르면 아무 의미가 없다. 판당 줄 수는 블록 형상 집합과 생성 정책이 좌우한다. 해금 수치 확정의 전제이므로 P0으로 올려야 한다. 최소 결정 항목:

1. **형상 집합**: 회전 불가이므로 방향별로 별개 형상. 예: 1×1, 1×2, 2×1, 1×3, 3×1, 2×2, 1×4, 4×1, 1×5, 5×1, L 4방향, T 4방향, 3×3 등. MVP 집합을 표로 확정.
2. **생성 정책**: 순수 균등 / 가방(bag) / 적응형 중 택일. 권고안: **가방 + "최소 1개 배치 가능" 보장**.
3. **보장 기준 보드**: 수동 모드에서 대기 줄이 있을 때 "현재 보드" 기준이면 대기 줄을 쥔 이용자가 더 쉬운 조각을 받는다(보류 행위 보상). **"대기 줄 제거 후 보드" 기준**을 권한다. 자동 모드에서는 두 기준이 같으므로 모드 중립적이다. 미정 항목으로 등재.
4. 자동/수동 각각 판당 줄 수·판당 시간·최대 동시 줄 분포를 시뮬레이션과 실측으로 수집.

### 9.2 첫 세션 스크립트 (성장기획 §22-1 구체화)

가정: 신규 이용자, 수동 기본, 판당 15~30줄. 이 가정은 §9.1 실측 후 교체.

| 시점 | 이벤트 | 화면 |
|---|---|---|
| 1판 초반 | 첫 2줄 동시 클리어 → 벽돌 빠른 해금 | 토스트 1줄 "벽돌 해금" |
| 10층 | 구간 1 완성 | 토스트 "구간 1 완성" (퍼즐 중단 없음) |

### 9.3 MVP 정의 권고

상위기획 §30 Phase 1(퍼즐 전용)만으로는 차별점을 검증하지 못한다. **MVP = Phase 1 + Phase 2 최소형**을 권한다.

- 이렇게 해야 성장기획 §18 검증 1·2가 가능하다.

## 10. 추가 발견 (Codex 미언급)

### A. Phase 번호 충돌

- 상위기획 §30: Phase 1 핵심 퍼즐 → 2 탑 성장 → 3 건축 표현 → 4 경쟁 → 5 확장.
- 성장기획 §19: Phase 1 성장 재미 검증(탑 포함) → 2 건축 소유감 → 3 경쟁 → 4 스타일 경쟁.
- 권고: 상위기획(v0.3, 최신)을 정본으로. 성장기획 §19는 "성장 검증 단계 A~D"로 개명하고 상위 Phase 2~5에 매핑하거나 삭제 후 참조.

### B. 수익모델 모순

§8.4 참조.

### C. 재질 해금 과속 리스크

수동이 기본값이므로 첫 판에 2줄 동시는 거의 확실, 3줄도 유력, 4줄은 1~3판 안에 나온다. 재질 4종이 **첫 세션에 전부 풀릴** 가능성이 높다. 그러면 장기 목표는 파츠뿐이다.

- 선택지: (a) 수용, 재질은 조기 폭, 파츠는 깊이로 역할 분담 / (b) 빠른 경로를 "N회"로 상향(예: 3회) 또는 크리스털을 5줄 이상으로 / (c) 탑 높이 소프트 게이트 추가.
- 권고 성향: (b). (c)는 "빠른 경로" 약속과 모순. 결정은 §9.1 실측 후. **미정 항목 등재.**

### D. 수동 모드의 구조적 점수 우위

수동에서는 배치 직후 즉시 클리어를 누르면 자동과 똑같이 플레이할 수 있다. 즉 수동 ⊇ 자동이고 점수 기대값은 수동 ≥ 자동이다. 문서의 "동일 산식"은 사실이지만 "동일 기대값"은 아니다.

- 권고: 상위기획 §5에 "자동은 편의 모드이며 점수 상한은 수동이 높다. 최고점 기록은 모드 구분 없이 단일"을 명시. 판 중 전환이 가능하므로 모드별 랭킹 분리는 실현 불가능하다는 근거 포함. 층수는 모드 중립이므로 성장 경쟁에는 영향 없음.

### E. 세이브 스키마 버전·마이그레이션 부재

상위기획 §29에 항목 목록만 있고 버전이 없다. `schema_version`과 "v(n)→v(n+1) 마이그레이션 함수 필수, 구버전 파일 로드 테스트 포함"을 P0으로 추가.

### F. "대기 중인 완성 줄"은 파생값

수동 모드의 대기 줄 = 현재 보드에서 완성된 모든 가로/세로 줄. 보드에서 언제나 계산 가능하다. 별도 저장하면 보드와 어긋날 경로가 하나 생긴다. §29에서 삭제하거나 "파생값, 저장하지 않음"으로 표기. 스트릭용 `batch_success`·`streak`은 저장 필요(§4.2).

### G. 구간 완성 연출 시점·기본 외형 미정

상위기획 §15와 성장기획 §11이 "완성 시 연출"을 말하지만 퍼즐 중인지 판 종료 후인지가 흐리다. 권고: 퍼즐 중 = 토스트만, 전체 연출 = 판 종료 후 또는 탑 화면 진입 시. 한 판에 구간 2개 이상 완성 시 묶음 연출 여부는 미정. 기본 외형은 §6.4 상속 규칙.
