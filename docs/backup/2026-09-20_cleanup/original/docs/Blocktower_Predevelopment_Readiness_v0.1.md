# Blocktower 개발 착수 전 조사·디자인 에셋 검토 v0.1

- 기준일: 2026-09-20
- 상태: 최초 조사 당시 기록. 현재 준비도와 실행 순서는 [v0.2](Blocktower_Predevelopment_Readiness_v0.2.md)를 따른다. 이후 목표 엔진 사전 테스트가 수행되었다.
- 기준: [상위기획 v0.4](Blocktower_Upper_Game_Design_v0.4.md), [성장 v0.3](Blocktower_Growth_System_Plan_v0.3.md), [스킨 v0.3](Blocktower_Visual_Bible_BlockSkin_Decision_v0.3.md)
- 기존 미결정 항목 D01~D14는 [레드팀 결정 기록](Blocktower_Redteam_Review_2026-09-20.md)을 참조한다. 본 문서는 준비 순서와 산출물을 구체화하며 기존 결정을 변경하지 않는다.

## 1. 판단

**규칙 실험용 프로토타입은 임시 그래픽으로 시작할 수 있다. 다만 조각 공급 명세, 실제 화면의 상태 표시, 실행 환경 정리가 선행되어야 한다.**
출시용 아트를 모두 준비한 뒤 개발을 시작할 필요는 없다. 먼저 B 블록·공통 UI·목재 임시 탑으로 퍼즐→성장 루프를 연결하고, 실제 손가락 조작과 첫 30층 경험을 검증한다.
현재 가장 큰 제작 위험은 예쁜 정적 비교 이미지에 맞춰 에셋을 양산한 뒤, 작은 화면의 대기 줄/프리뷰/탑 이음새 문제로 다시 만드는 것이다.

## 2. 현재 보유 자료와 개발 환경

현재 작업 폴더는 docs만 존재한다. 게임 프로젝트와 실행 가능한 프로토타입은 확인되지 않았다.

| 항목 | 확인된 사실 | 판단 / 필요한 조치 |
|---|---|---|
| 기획 | 상위·성장·스킨 결정·검토 기록 존재 | 규칙 방향은 충분하지만 D01~D14 결정과 실험 결과가 필요 |
| 디자인 이미지 | B/C 비교 PNG 1장 | 콘셉트 참고용. 분리된 셀·아이콘·탑 에셋과 제작 원본 없음 |
| UI/아트 규격 | 전체 Visual Bible, 폰트 파일, 색상 토큰, 실제 HUD 시안 없음 | 최소 규격과 상태별 시안을 먼저 준비 |
| 탑 | .blend 및 구간 렌더 파일 없음 | 목재 한 종류의 합성 샘플부터 검증 |
| 소리 | 효과음·음악 파일 없음 | 조작 피드백용 임시 효과음부터, 음악은 후순위 |
| Godot | PATH의 `godot --version`은 `4.6.1.stable.official.14d19694e` | 기획의 4.7.2와 불일치. 사용할 실행 파일 경로와 버전을 고정 |
| 내보내기 템플릿 | 사용자 표준 폴더에서 `4.6.1.stable` 확인 | 기획 기준 버전의 템플릿 준비 필요 |

| Android SDK | 표준 SDK 폴더의 adb 존재; PATH에서는 발견 안 됨 | 새로 전부 설치하기보다 Godot에 경로 지정 후 필요한 패키지 대조 |
| SDK 패키지 | platforms 34/35/36, build-tools 35.0.0/36.0.0/36.1.0, NDK 27.1.12297006/28.2.13676358 | ‘최신이 있으니 호환’으로 간주하지 않음. 목표 엔진 기준으로 확인 |
| Blender | PATH와 `C:/Program Files/Blender Foundation`에서 확인 못 함 | 다른 설치 위치까지 조사한 것은 아님. 프리렌더 작업 전에 실행 경로 확인 |
| 버전 관리 | 현재 폴더에서 Git 저장소가 확인되지 않음 | 코드 착수 때 저장소·무시 규칙·아트 원본 보관 방식 준비 |

점검은 PATH, 표준 설치 경로, 현재 폴더에 한정했다. 다른 디스크의 에셋·실행 파일이나 보유 테스트 기기를 전수 조사한 결과가 아니다.
엔진 업그레이드·SDK 설치·저장소 초기화는 이번 검토에서 수행하지 않았다.

## 3. 개발 전 필요한 조사와 완료 조건

‘선행’은 전체 프로젝트를 멈추라는 뜻이 아니라 해당 작업의 기준을 먼저 정하라는 의미다. 밸런스 확정은 프로토타입 측정 이후다.

| 순서 | 조사 / 해결할 질문 | 방법과 산출물 | 완료 조건 / 연결 항목 |
|---|---|---|---|
| 1 | 누구를 위한 몇 분짜리 게임인가? 첫 검증 플랫폼·세로/가로·최소 화면은? | 타깃/세션 가설 1장, 실제 테스트 기기 목록 | 플랫폼·방향·기기·관찰 과제의 첫 실험 기준 결정. D01/D02/D11 |
| 2 | 어떤 조각을 어떤 확률로 공급하는가? | 조각 ID·셀 좌표·방향·중복·가중치·시드·시작 묶음 데이터 표 | 실험용 카탈로그와 공급 정책 1개를 버전 고정. 최종 난이도 확정과 구분. D03 |
| 3 | 수동 클리어를 이해하고 편하게 누르는가? | 실제 크기 HUD 시안으로 드래그/프리뷰/막힘 해소/토글 관찰 | 새 줄·대기 줄·배치 불가를 구분하고 드롭과 클리어 오입력 원인을 수정. D02/D06 |
| 4 | 목표 엔진으로 실제 폰에서 실행·저장되는가? | 빈 화면+터치+저장 검증용 작은 기술 샘플, 환경 버전표 | 기기 설치·실행·백그라운드/복귀·종료 후 저장 복원 확인. 상위 35절 |
| 5 | 점수 외에 탑을 보고 싶은 이유가 생기는가? | B+목재 임시 탑으로 첫 10/30층 관찰; 모드 순서 교차 | 도달 실패도 포함해 시간·자발적 탑 방문·편집·재시도 기록. D04/D12 |
| 6 | 자동만 써도 원하는 재질과 파츠에 도달 가능한가? | 같은 공급 버전/시드 집합에서 모드별 실험과 사람 관찰 | 재질+파츠 해금까지 시간/판 수/포기 사례표. 관찰 후 요구량 조정. D04/D05 |
| 7 | 탑 모듈이 조립·확대·축소되어도 자연스러운가? | 목재 1종: 층 타일과 10층 프리셋 비교, 1/9/10/11/30층 합성 | 앵커·부분 구간·지붕·그림자 검증 후 제작 방식 결정. D07 |
| 8 | 3,000층과 C 연출에서 성능이 유지되는가? | 반복 모듈/축약 뷰로 스트레스 샘플, B/C 동일 장면 실기기 측정 | 메모리·프레임 시간·텍스처 예산과 기기별 한도 기록. 아트 양산 전에 수행. D08 |

추가로 짧은 참고작 조사를 권한다. 블록 배치 퍼즐 2종, 수동 실행/보류 판단 게임 1종, 영구 꾸미기 게임 1종을 실제 사용해 입력 방식·실패 후 화면·다음 목표·선택 편집 흐름을 비교한다.
산출물은 패턴 비교표 1장과 Blocktower에 채택/배제할 이유다. 스크린샷의 색·형태를 그대로 제작 규격으로 옮기지 않는다. 이번 검토에서는 경쟁작 직접 플레이나 이용자 인터뷰를 수행하지 않았다.

## 4. 공식 자료 조사로 확인한 기술·조달 방향

### 실행 환경과 렌더러

기획 기준인 4.7.2는 [공식 릴리스 아카이브](https://godotengine.org/download/archive/4.7.2-stable/)를 기준으로 실행 파일과 내보내기 템플릿을 맞춘다. 로컬 4.6.1을 이미 4.7.2로 준비된 환경으로 취급하지 않는다.

Godot의 Android 안내는 OpenJDK 17을 권장하면서 상위 JDK도 지원한다고 설명한다. 현재 JDK 25를 무조건 제거하거나 장애 원인으로 단정하지 않는다. 별도 JDK 17 경로를 사용할지 포함해 테스트 빌드로 선택한다. SDK/NDK의 세부 버전은 실제 고정한 엔진과 템플릿 기준으로 대조한다. [Godot Android 내보내기 문서](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_android.html)

iOS 내보내기에는 macOS와 Xcode 환경이 필요하다. 현재 Windows 환경만으로 iOS 빌드 준비가 완료된 것은 아니다. 따라서 **Android를 첫 기술 검증 대상으로 삼는 안**이 현재 환경에서 적은 준비로 시작할 수 있다는 판단이다. 출시 순서를 확정한 것은 아니다. [Godot iOS 내보내기 문서](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_ios.html)

2D와 저사양 모바일을 고려하면 Compatibility를 최초 비교 기준으로 권한다. Mobile 렌더러와 같은 보드/투명 탑/클리어 효과를 비교해 선택한다. ‘모바일 게임’이라는 이름만으로 Mobile 렌더러를 고르지 않는다. 이는 공식 선택 가이드를 Blocktower에 적용한 제안이며 실측 결과는 아니다. [Godot 렌더러 안내](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)

Godot은 SVG를 기본적으로 가져오기 시 래스터화하며 지원 기능에 제한이 있다. PNG/WebP 원본 파일이 작다고 GPU 메모리도 작아지는 것은 아니다. 따라서 얇은 프레임은 실제 가져오기 결과를 확인하고, 탑 축소에 필요한 mipmap/필터/압축은 UI와 별도로 정한다. [Godot 이미지 가져오기 문서](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_images.html)

`stable` 문서는 이동하는 별칭이다. 이 링크의 최신 패키지 목록을 다른 Godot 버전에 그대로 복사하지 말고, 버전 고정 시 확인한 요구사항과 날짜를 환경표에 기록한다.

무료 UI 팩은 조작 검증 속도를 높이는 재료다. 조립 규격이 없는 3D 건물 팩을 대량 구매하면 Blocktower 탑에 맞추는 수정 비용이 더 커질 수 있다.

## 5. 먼저 준비할 최소 디자인 에셋

현재 아래 항목은 모두 게임 투입용 파일로는 미준비다. 표의 수량은 **제작 범위 제안**이며 발주 확정 수량이 아니다. 상태별 표현은 별도 이미지 대신 공통 도형/스타일/색상으로 재사용할 수 있다.

| ID | 에셋 / 최소 구성 | 파일·형태 제안 | 언제 필요한가 / 수용 기준 |
|---|---|---|---|
| A01 | 최소 디자인 규격 1세트: 팔레트 역할, 글꼴/굵기, 숫자, 모서리, 선, 간격, 상태 대비 | 편집 가능한 규격표+토큰 데이터 | UI 제작 전. B/C 장식보다 상태 표시의 시각적 우선순위 고정 |

| A07 | 최소 목재 탑: 반복 층, 기단, 구간 경계 마감, 최상단 마감 | 처음은 도형 가능; 아트 검증은 투명 PNG+.blend | 퍼즐→탑 검증에 필요. 1/9/10/11층을 정확히 보여 주고 지붕 충돌 없음 |
| A08 | 피드백 1세트: 배치·클리어·+층·구간 완성 | 짧은 시간표/키 프레임 명세, 단순 파티클 원본 | 정적인 상태표 후 준비. 입력 가능 시점·모션 감소·동시 알림 순서 명시 |
| A09 | 임시 효과음 약 6종: 선택/버튼, 배치, 배치 거절, 클리어, 구간 완성, 게임오버 | 편집용 WAV 및 적용 설정표 | 첫 체험 평가 전. 연타 시 과도한 중첩 방지, 무음 상태에서도 정보 전달 |

**당장 만들 최소 묶음은 A01~A07이다.** A08/A09는 퍼즐과 탑이 연결된 첫 체험 평가까지 준비한다. 이 단계에 배경 음악, 상점 아트, 모든 재질 파츠가 필수는 아니다.

## 6. 화면 시안과 아트 검증용 추가 에셋

화면 시안은 통짜 배경 이미지로 납품하지 않는다. 편집 가능한 레이아웃, 재사용 컴포넌트, 문구 목록을 함께 제공한다.
현재 가안인 논리 크기 360×800을 시작으로 320×568, 412×915에서 확인하고, 화면 방향 결정 후 기준을 고정한다. 픽셀 크기와 터치 물리 크기는 별개이므로 실기기 확인이 필요하다.

| 순서 | 준비할 화면/에셋 | 확인해야 할 상태 |
|---|---|---|
| 1 | 기본 퍼즐 전체 화면 | 점수/최고점·토글·8×8·3조각·클리어 버튼·성장 표시 동시 노출 |
| 2 | 퍼즐 상태 비교판 | 대기 1줄, 교차 2줄, 교차 4줄+프리뷰, 전 조각 불가+대기 있음, 게임오버 |
| 3 | 전환/복귀/결과 흐름 | 자동 전환 확인/취소, 게임오버 후 재시작/탑 선택, 저장 실패/복구 안내 |
| 4 | 탑과 구간 편집 화면 | 0/9/10/13/30층, 부분 구간, 대표 선택, 잠긴 재질의 두 해금 경로 |
| 5 | C 비교 셀 1종과 동일 상태판 | B와 같은 보드·상태·정보량으로 밴드 오인 검사. 상품용 효과 양산 전 |
| 6 | 목재+벽돌 연결 샘플, 이후 4재질 기본 프리셋 | 다른 재질 구간의 경계·빛·폭·그림자 일치; 1개 파츠의 해금/적용 검증 |
| 7 | 축약 탑 뷰 샘플 | 300/3,000층 총 높이와 구간 점프. 전체를 단순 축소해 모두 안 보이는 실패 방지 |

1~4는 최소 플레이 흐름 검증, 5~7은 C 스킨 및 본격적인 탑 아트 제작 전 검증이다.
기존 PNG의 설명/보드 겹침은 비교판을 다시 배치할 때 해결한다. 원본을 잘라 게임 에셋으로 사용하지 않는다.

## 7. 에셋 제작 전에 고정할 납품 규격

| 영역 | 반드시 정할 항목 |
|---|---|
| 공통 | 에셋 ID·버전, 원본/내보내기 경로, 기준 크기/표시 배율, 수정 가능한 원본, 라이선스 |
| 퍼즐 | 셀 크기·간격·앵커, 외곽/내부선 두께, 프리뷰 위치, 드래그 오프셋, 상태 오버레이 순서 |
| UI | 패널 늘림 영역, 최소 터치 영역, 안전 영역, 글꼴 확대·긴 한국어/영문 처리, 텍스트를 이미지에 굽지 않는 원칙 |
| 탑 | 카메라 투영/각도, 층 높이·폭, 상하 결합 앵커, 광원·노출·색 관리, 투명 여백, 레이어 순서·그림자 처리 |
| 가져오기 | 색 공간·알파 가장자리, 필터·mipmap·압축, 아틀라스 여백, 실제 가져온 텍스처 메모리 |
| 피드백 | 상태 변화 시작/종료, 보드 정보 유지, 입력 잠금 길이, 효과음 동시 재생, 진동/모션 감소 설정 |

탑은 같은 .blend 장면/카메라/조명 프리셋에서 재생성 가능해야 한다. 구간마다 따로 만든 이미지나 AI 콘셉트 이미지가 자연스럽게 이어질 것이라고 가정하지 않는다.
AI 이미지를 활용한다면 무드/재질 탐색용으로 먼저 쓰고, 최종 조립 모듈은 고정된 제작 규격에 맞춰 제작한다.
실시간 게임에는 프리렌더 결과를 쓰며, 원본 3D 파일을 런타임 필수 에셋으로 추가하지 않는다.

## 9. 권장 실행 순서와 착수 기준

> 이 절은 최초 제안 이력이다. 아래 기기 실행·HUD 준비를 코드 뼈대 작성 전 필수 조건으로 해석하지 않는다. 현재는 v0.2의 G0(코드 착수)와 G1(사람 플레이)을 구분해 진행한다.

1. 플랫폼/기기/화면 가안과 조각 공급 실험 버전을 정한다.
2. 사용할 Godot/템플릿/Android 도구 경로를 맞추고 기술 샘플을 실제 기기에서 실행한다.
3. A01~A07 및 기본 퍼즐·탑 화면을 준비하고, 상태 판독/오입력을 확인한다.
4. B+목재로 최소 루프를 구현하면서 A08/A09를 적용한다. 첫 10/30층 관찰 후 성장 수치를 조정한다.
5. 목재+벽돌 합성 샘플과 C 비교판이 통과하면 4재질 기본 아트와 추가 파츠를 제작한다.

첫 구현의 준비 완료는 다음 증거로 판단한다.

- [ ] 버전이 고정된 조각 목록/공급 정책과 판정·저장 계약이 있다.
- [ ] 지정한 엔진과 템플릿으로 목표 기기에 실행한 기록이 있다.
- [ ] 최소 화면·터치 영역·안전 영역 기준과 기본 HUD/탑 레이아웃이 있다.
- [ ] B 셀·공통 상태 표시·기본 UI·글꼴·목재 임시 탑을 조합해 사용할 수 있다.
- [ ] 자산 출처/원본과 코드 변경을 보존할 위치 및 버전 관리 방식이 정해졌다.
- [ ] 첫 30층에서 무엇을 관찰하고 어떤 문제면 수정할지 기록되어 있다.

현재 위 항목은 문서로 정의된 부분과 실제 준비/실행이 필요한 부분이 섞여 있다. 체크박스는 실제 증거가 생긴 뒤 완료 처리한다.
